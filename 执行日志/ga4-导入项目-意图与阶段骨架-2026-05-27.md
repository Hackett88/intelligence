# GA4 数据导入项目 · 意图与阶段骨架

## 0. 意图（开始的初衷，走偏时回来看）

把真实 GA4 数据接进「收录与索引」，替换抽屉里的 `mockGa4ForPage` 示例值，让 4 个保留字段
（互动率 / 活跃用户 / 平均互动时长 / 来源国 Top10）展示真实数据。

**Sean 的硬性约束（原话拆解）：**
1. **复用 GSC 那套逻辑方案** —— 即浏览器驱动（puppeteer-core 连本地 Chrome CDP 9222，骑用户已登录的会话，无需独立 API 凭证），不另起炉灶。
2. **按日 / 周 / 月的算法采集** —— 复用 `classifyCadence`（daily/weekly/monthly），与 GSC 同一套分档。
3. **最终写入到 GSC 更新中，与 GSC 数据一起更新** —— 不是独立管道，而是并入现有 sync 流：一次 sync 同时拿 GSC + GA4，存同一批次、同一行，一起展示。
4. **分阶段，每阶段做足准备；逐阶段测试验证确认后才进下一阶段。**
5. **生产级，安全稳定。**

**最终成功标准：** 成功的测试 —— 全部 GA4 字段数据真实导入并在抽屉展示，且整条流程每一阶段都过了测试验证。

## 1. 现状摸底结论（GSC 那套方案到底是什么）

读穿了现有管道，"GSC 那套逻辑方案"= 浏览器驱动抓取：

| 环节 | 实现 | 文件 |
|---|---|---|
| 采集 | puppeteer-core `connect` 本地 Chrome（CDP 127.0.0.1:9222），导航 GSC Performance 页，**抓渲染出来的 HTML 表格 DOM**（`table.i3WFpf tbody tr`），解析中文数字格式 | `src/lib/gsc/fetcher.ts` |
| 编排 | `POST /api/indexing/sync`：连浏览器→抓页面级 4 指标→按 mode 决定爬哪些页的逐页关键词→落库 | `src/app/api/indexing/sync/route.ts` |
| 节奏 | `classifyCadence(关键词数, 页面类型, url)` → daily(词≥6核心页) / weekly(词少或暂无) / monthly(资源/系统/目录/政策页)。mode=daily/weekly 只爬该档页，基准取最近一次 full 批次 | `src/lib/gsc/classify.ts` |
| 落库 | PG：`gsc_sync_log`(批次) + `gsc_pages`(每真实页一行，唯一键 batch_id+url)；JSON 兜底 `data/gsc-snapshot.json` | `src/db/schema.ts` / `src/lib/gsc/repository.ts` / `store.ts` |
| 读取 | `loader.ts` 优先读最新 PG 批次→重建合成节点+parentId→喂给抽屉；60s 内存缓存 | `src/lib/gsc/loader.ts` |
| 部署守卫 | `NODE_ENV=production` 直接 403（线上无本地 Chrome），只能本地跑 | route.ts |

**关键推论 —— GA4 该怎么并入：**
- GA4 也走浏览器（同一个已登录 Chrome 同时登着 GA4 和 GSC），在同一次 sync 里、同一个 CDP 连接内顺带把 GA4 per-URL 指标拿到。
- GA4 数据按 URL path 与 GSC 行对齐（已验证 path 一致），写进**同一行 `gsc_pages`**（扩 4~N 个 GA4 列），同一批次。
- cadence 共用 `classifyCadence` —— 一个 URL 是日/周/月更，GSC 和 GA4 同档同步。
- 读取端 `loader.ts` 把 GA4 列映射进 `PageRow.ga4`，抽屉读真实值而非 mock。

## 2. 唯一的关键未知（阻塞一切，Stage 1 必须先定）

**GA4 per-URL 数据怎么从已登录浏览器里可靠、准确地拿出来？** 三条候选，需实测定夺：
- (A) **复刻 DOM 抓取**：导航 GA4 标准报告「网页和屏幕」（已确认是可访问的 HTML grid），切 dimension=网页路径、配指标，抓表格。最贴近 GSC 方案，但 GA4 是重 SPA、虚拟滚动/canvas 多，且互动率不在默认列、来源国需 page×country 交叉。
- (B) **重放 GA4 内部数据接口**：GA4 UI 自身拉数走的内部 batchGet/GenerateReportData 端点，在页面上下文里带着登录态 + xsrf 直接 fetch，拿结构化 JSON。最稳、最准、可任意指定维度指标，但要逆向请求格式。
- (C) **官方 GA4 Data API**（analyticsdata.googleapis.com）：最规范，但需 OAuth/service-account 凭证 —— **违背"复用 GSC 无凭证方案"的约束**，仅作兜底备选。

→ Stage 1 用小范围实测对比准确性，定出主方案（倾向 B，A 兜底）。

## 3. 分阶段骨架（每阶段都有门禁：测试验证确认 → 才进下一阶段）

```
Stage 0  现状摸底（GSC 方案吃透）                      ✅ 已完成（见 §1）
   │
Stage 1  小范围导入测试 + 准确性验证   ← 当前
   │   · 选 3–5 个代表 URL（首页/阿语长文/产品页/低流量页）
   │   · 用候选方案(B优先)拉这几个 URL 的 GA4 字段
   │   · 与 GA4 UI 显示值逐项比对 → 误差在可接受范围
   │   · 同时定下：口径(per session / organic 收窄 / 28d)、字段映射
   │   【门禁：Sean 确认"数据准、方案可行"】
   │
Stage 2  方案规划与详设（组队）                        ⬜
   │   · researcher/coddy/Plan 协作：采集方案、schema 设计、sync 集成点、回滚预案
   │   · 产出：架构骨架 + 分层 todo + 风险/回滚
   │   【门禁：Sean 拍板骨架】
   │
Stage 3  数据库 schema 扩展（GA4 列）                  ⬜
   │   · gsc_pages 加 GA4 列 + migration；本地/测试库先行，生产库先方案后授权
   │   【门禁：migration 在本地跑通 + 可回滚验证】
   │
Stage 4  GA4 采集器（ga4-fetcher）                     ⬜
   │   · 镜像 fetcher.ts：CDP 连接 + per-URL GA4 拉取 + 并发 + 重试 + 容错
   │   · 单测 / 小批集成测：抓 N 个 URL 数据正确
   │   【门禁：test-runner 跑通，数据与 UI 一致】
   │
Stage 5  并入 sync 流（与 GSC 一起更新）               ⬜
   │   · sync/route 在同批次内合并 GA4，按 cadence 同档；落同一行
   │   · daily/weekly/full 三档各跑通；carry 逻辑兼容
   │   【门禁：三档同步集成测全绿】
   │
Stage 6  读取端 + 前端接真实数据                       ⬜
   │   · loader 映射 GA4 列→PageRow.ga4；抽屉去 mock、读真实；基准(同类型分位)可后续
   │   【门禁：抽屉全字段展示真实数据，浏览器实测】
   │
Stage 7  全链路验收（生产级）                          ⬜
       · 端到端：一次 sync → GSC+GA4 同落 → 全字段展示
       · 全部 GA4 字段导入并展示 = 最终成功标准
       【门禁：Sean 验收】
```

## 4. 安全与门禁纪律

- **生产写操作（生产库 migration、生产数据写入）必须先方案后授权**，不擅自动生产。
- 每阶段产出 = 真实交付物 + 执行日志 + 留痕（测试报告/截图），落 `执行日志/`。
- 撞墙即停、按层回流；单阶段未过门禁不进下一阶段。
- 采集只读 GA4，不改 GA4 任何配置；不动用户已开的 GSC/GA4 标签页（只读其会话）。

## 5. 团队编组（调度 = 我，执行 = 各 Agent）

- **researcher** —— GA4 数据提取方法论（内部接口 vs DOM vs 官方API；准确性/稳定性/凭证权衡）。Stage 1–2。
- **coddy** —— 架构第二意见（并入 GSC 流的设计、回滚预案）。Stage 2。
- **Plan** —— 详设收敛（分层 todo、关键文件、调用顺序）。Stage 2。
- **database-manager** —— schema migration。Stage 3。
- **app-backend** —— ga4-fetcher + sync 集成。Stage 4–5。
- **app-frontend** —— loader/抽屉接真实数据。Stage 6。
- **test-runner** —— 每阶段门禁核查。全程。
- **browser-executor / 我** —— 实际浏览器数据提取与取证。Stage 1、4。
